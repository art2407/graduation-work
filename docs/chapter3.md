# 3. РЕАЛИЗАЦИЯ И ЭКСПЕРИМЕНТАЛЬНОЕ ИССЛЕДОВАНИЕ

## 3.1 Реализация серверной части веб-приложения

### 3.1.1 Реализация бизнес-логики учёта и координации мероприятий

Серверная часть веб-приложения реализована на платформе Node.js с использованием фреймворка NestJS версии 10. NestJS обеспечивает модульную организацию кода, строгую типизацию на основе TypeScript и декларативный стиль описания маршрутов, валидации и авторизации посредством декораторов.

Серверное приложение организовано в виде набора функциональных модулей, каждый из которых инкапсулирует контроллеры, сервисы и репозитории конкретной предметной области. В состав серверной части входят следующие модули:

– `AuthModule` — аутентификация и управление токенами доступа;

– `UsersModule` — управление учётными записями и профилями пользователей;

– `EventsModule` — создание, редактирование, модерация и отображение мероприятий;

– `RegistrationsModule` — регистрация участников, отмена записи и учёт посещаемости;

– `NotificationsModule` — управление push-подписками и отправка уведомлений;

– `ReferencesModule` — предоставление справочных данных (типы мероприятий, список институтов).

Реализация каждого модуля соответствует паттерну Controller-Service-Repository, описанному в главе 2. Контроллер принимает входящий HTTP-запрос и делегирует обработку сервису; сервис реализует бизнес-логику и обращается к репозиторию; репозиторий взаимодействует с СУБД PostgreSQL через ORM-инструмент Prisma.

Аутентификация пользователей реализована на основе механизма JSON Web Token (JWT) с применением библиотеки `@nestjs/passport` и стратегии `passport-jwt`. При успешном входе сервер формирует два токена:

– access-токен со сроком действия 15 минут, содержащий идентификатор пользователя и его роль;

– refresh-токен со сроком действия 7 суток, хранящийся на стороне сервера и используемый исключительно для выпуска нового access-токена.

Хранение паролей реализовано с использованием алгоритма хэширования bcrypt с коэффициентом стоимости 10, что исключает возможность восстановления оригинального пароля при компрометации базы данных.

Для защиты маршрутов применяется механизм Guard библиотеки NestJS. Декоратор `@UseGuards(JwtAuthGuard)` проверяет наличие и корректность JWT в заголовке запроса `Authorization: Bearer <token>`. Декоратор `@Roles(UserRole.ORGANIZER)` в связке с `RolesGuard` дополнительно проверяет роль пользователя.

Валидация входящих данных осуществляется на уровне DTO (Data Transfer Object) с использованием библиотеки `class-validator`. Глобальный `ValidationPipe` автоматически применяет объявленные правила ко всем входящим запросам и возвращает структурированный ответ с перечнем ошибок при их наличии.

Модуль мероприятий реализует следующую бизнес-логику учёта:

– при создании мероприятия организатором ему присваивается статус `MODERATION`, после чего событие помещается в очередь на проверку администратором;

– при публикации мероприятия администратором статус меняется на `PUBLISHED`, а в очередь BullMQ добавляется задача отправки push-уведомлений подписчикам;

– при регистрации участника проверяется наличие доступных мест (сравнение текущего числа подтверждённых регистраций с полем `capacity`); в случае превышения лимита запрос отклоняется с HTTP-статусом 409 Conflict;

– при отмене мероприятия организатором всем зарегистрированным участникам автоматически отправляется push-уведомление.

### 3.1.2 Реализация механизмов регистрации и уведомлений

Модуль регистрации обеспечивает учёт записей студентов на мероприятия. При каждой операции регистрации сервис выполняет следующую последовательность действий:

1. Проверка существования мероприятия и его статуса (`PUBLISHED`).
2. Проверка отсутствия повторной регистрации данного пользователя (уникальность пары `eventId + userId` обеспечена ограничением `@@unique` в схеме Prisma).
3. Проверка дедлайна регистрации (поле `registrationDeadline`).
4. Проверка доступности мест с учётом `capacity`.
5. Создание записи `Registration` со статусом `CONFIRMED`.
6. Постановка задачи отправки подтверждающего уведомления в очередь BullMQ.

Механизм чек-ина (отметки посещения) реализован через отдельный эндпоинт `PATCH /registrations/:id/checkin`. Организатор или администратор вызывает данный эндпоинт вручную или через сканирование QR-кода, содержащего идентификатор регистрации. При успешном чек-ине запись получает значения `checkedInAt` (временная метка) и `checkInSource` (`MANUAL` или `QR_SCAN`), а статус меняется на `ATTENDED`.

Система уведомлений построена на стандарте Web Push API и обеспечивает доставку сообщений непосредственно в браузер пользователя без необходимости установки нативного приложения. Архитектура системы уведомлений включает следующие компоненты:

– хранилище подписок в таблице `PushSubscription` (endpoint, ключи p256dh и auth);

– очередь задач на основе BullMQ с Redis в качестве брокера;

– обработчик очереди (Worker), выполняющий отправку посредством библиотеки `web-push`.

При наступлении триггерного события (публикация, отмена или изменение мероприятия) сервис добавляет задачу в очередь. Воркер извлекает задачу, формирует полезную нагрузку уведомления в формате JSON (заголовок, тело, ссылка для перехода) и осуществляет отправку по всем активным подпискам затронутых пользователей. Использование очереди гарантирует повторную попытку отправки при временном сбое и предотвращает блокировку основного потока обработки запросов.

## 3.2 Реализация клиентской части веб-приложения

### 3.2.1 Реализация пользовательского интерфейса

Клиентская часть веб-приложения реализована в виде SPA (Single Page Application) на основе библиотеки React версии 18 с инструментом сборки Vite версии 5. Применение Vite обеспечивает мгновенный запуск сервера разработки за счёт использования нативных ES-модулей и сборку продуктового бандла с оптимальным размером артефактов посредством Rollup.

Структура исходного кода организована по методологии Feature-Sliced Design (FSD), предусматривающей разделение на слои: `shared` (общие утилиты и компонент API-клиента), `entities` (доменные объекты), `features` (пользовательские сценарии) и `pages` (маршрутизированные страницы).

Для построения пользовательского интерфейса использована библиотека компонентов Material UI (MUI) версии 5, реализующая спецификацию Material Design. Применение готовой библиотеки компонентов обеспечивает визуальную согласованность интерфейса и соответствие требованиям доступности (WCAG 2.1).

Навигация между страницами реализована на основе библиотеки React Router v6. Маршрутизация сконфигурирована с разделением страниц по ролям: незащищённые маршруты (`/login`, `/register`) доступны без аутентификации; защищённые (`/events/create`, `/profile`, `/admin`) проверяют наличие токена через компонент `RequireAuth`.

Управление глобальным состоянием аутентификации реализовано с использованием библиотеки Zustand. Хранилище содержит данные текущего пользователя (идентификатор, роль, email) и методы `login` / `logout`, обновляющие состояние и управляющие хранением токенов в `localStorage`.

Управление состоянием серверных данных (кэширование, инвалидация, фоновое обновление) реализовано посредством TanStack Query (React Query) версии 5. Это позволяет декларативно описывать запросы к API через хук `useQuery`, автоматически повторять запросы при сетевых ошибках и инвалидировать кэш при выполнении мутаций через `useMutation`.

Для реализации форм применяется библиотека React Hook Form в сочетании со схемой валидации Zod. Данный подход обеспечивает:

– декларативное описание правил валидации непосредственно в схеме TypeScript;

– синхронную валидацию на стороне клиента до отправки запроса на сервер;

– автоматическое отображение сообщений об ошибках в полях формы при нарушении правил.

### 3.2.2 Интеграция клиентской части с сервером

Взаимодействие фронтенда с серверным REST API реализовано через централизованный API-клиент на основе библиотеки Axios. Клиент инстанцируется с базовым URL `/api` и настроенными интерсепторами (перехватчиками запросов и ответов).

Интерсептор запросов автоматически добавляет заголовок `Authorization: Bearer <token>` к каждому исходящему запросу, извлекая access-токен из хранилища Zustand. Интерсептор ответов перехватывает ошибку 401 (Unauthorized), выполняет запрос на обновление токена через `POST /auth/refresh`, и повторяет исходный запрос с новым токеном. Если обновление токена также возвращает ошибку (refresh-токен истёк), пользователь перенаправляется на страницу входа. Данная схема обеспечивает прозрачное для пользователя обновление сессии.

API-клиент организован в виде модулей, соответствующих серверным контроллерам: `eventsApi`, `registrationsApi`, `authApi`, `usersApi`, `referencesApi`. Каждый модуль предоставляет типизированные методы, возвращающие Promise с конкретным типом ответа, что обеспечивает безопасность типов от серверной схемы до компонента интерфейса.

Конфигурация Vite предусматривает проксирование запросов к `/api` на адрес серверного приложения `http://localhost:4000` в режиме разработки, что позволяет избежать проблем с политикой CORS при локальной разработке.

## 3.3 Реализация механизмов координации

### 3.3.1 Реализация уведомлений и напоминаний

Механизм координации участников мероприятий строится на своевременном информировании пользователей о релевантных событиях. В системе реализованы следующие типы push-уведомлений:

– уведомление о публикации нового мероприятия (рассылается всем активным пользователям при наличии подписки);

– подтверждение регистрации (отправляется участнику после успешной записи);

– напоминание о начале мероприятия (отправляется зарегистрированным участникам за 24 часа до начала);

– уведомление об отмене мероприятия (рассылается всем зарегистрированным участникам);

– уведомление об изменении ключевых параметров (дата, время, адрес).

Технически отправка уведомлений реализована следующим образом. При первом посещении приложения браузер запрашивает разрешение на получение уведомлений. При согласии пользователя JavaScript-код регистрирует подписку через `PushManager.subscribe()` и направляет объект подписки (содержащий endpoint и ключи VAPID) на сервер через `POST /notifications/subscribe`. Сервер сохраняет подписку в таблице `PushSubscription`.

При наступлении события сервис уведомлений формирует задачи в очереди BullMQ для каждой активной подписки затронутого пользователя. Воркер, работающий в отдельном потоке Node.js, извлекает задачи и выполняет отправку через библиотеку `web-push`, используя VAPID-ключи для аутентификации сервера у push-провайдера (Google FCM, Mozilla Autopush и др.).

### 3.3.2 Обработка изменений расписаний

Изменение параметров мероприятия (дата начала, адрес проведения) является критическим событием с точки зрения координации. При обновлении организатором полей `startAt`, `endAt` или `address` сервис автоматически определяет факт изменения, сравнивая новые значения с текущими в базе данных.

При обнаружении изменений выполняется следующая последовательность действий:

1. Обновление записи в таблице `Event` с новыми значениями.
2. Выборка всех регистраций со статусом `CONFIRMED` для данного мероприятия.
3. Формирование персонализированных задач уведомления в очереди BullMQ для каждого зарегистрированного участника с указанием изменившихся полей.
4. Воркер отправляет уведомление вида: «Мероприятие [название] перенесено. Новая дата: [дата]. Новый адрес: [адрес]».

Данный подход гарантирует, что ни один зарегистрированный участник не пропустит важное изменение расписания, а организатор освобождается от необходимости вручную уведомлять каждого записавшегося.

### 3.4.2 Оценка корректности учёта мероприятий и регистрации участников

Для проверки корректности механизмов учёта были проведены сквозные испытания полного жизненного цикла мероприятия:

**Этап 1. Создание и модерация.** Организатором создано тестовое мероприятие «Хакатон ИВТ-2026» с лимитом 3 участника. Система корректно присвоила статус `MODERATION`. Администратор опубликовал мероприятие; статус изменился на `PUBLISHED`.

**Этап 2. Регистрация участников.** Три студента последовательно зарегистрировались на мероприятие. После третьей регистрации система вернула счётчик `0 свободных мест`. Четвёртый студент при попытке регистрации получил ошибку 409. Проверка таблицы `Registration` подтвердила наличие ровно трёх записей со статусом `CONFIRMED`.

**Этап 3. Учёт посещаемости.** После начала мероприятия организатор отметил двух участников как присутствующих. Один участник не пришёл. Система корректно отразила итог: 2 посетителя со статусом `ATTENDED`, 1 — `CONFIRMED` (не отмечен). После ручного изменения статуса последнего на `NO_SHOW` данные учёта посещаемости приобрели завершённый вид.

**Этап 4. Изменение расписания.** Организатор изменил дату мероприятия. Система сформировала задачи уведомлений для двух подписчиков с активными push-подписками. Оба уведомления были доставлены в течение 3 секунд после сохранения изменений.

Все этапы сквозного испытания завершены без ошибок, что подтверждает корректность реализованных механизмов учёта мероприятий и управления участниками.

### 3.5.1 Интерпретация результатов тестирования

По результатам функционального тестирования все 17 запланированных тест-кейсов пройдены успешно, что свидетельствует о полноте реализации заявленных функциональных требований. Сквозное испытание жизненного цикла мероприятия подтвердило корректность взаимодействия всех подсистем: модуля создания и модерации, регистрации, чек-ина и уведомлений.

Тестирование устойчивости выявило корректную обработку граничных случаев во всех восьми проверенных сценариях. Особого внимания заслуживает результат ST-05: временная недоступность Redis не приводит к отказу основного функционала системы, поскольку очередь уведомлений является асинхронной и не блокирует обработку HTTP-запросов. Это соответствует принципу graceful degradation — система деградирует лишь в части дополнительного функционала, сохраняя работоспособность основных сервисов.

Реализованный механизм защиты от SQL-инъекций (результат ST-07) обеспечивается архитектурным решением: использование Prisma ORM исключает возможность передачи пользовательских данных непосредственно в SQL-запрос, поскольку все параметры обрабатываются как типизированные значения, а не строки запроса.
