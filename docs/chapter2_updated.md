# 2. ПРОЕКТИРОВАНИЕ ВЕБ-ПРИЛОЖЕНИЯ УЧЁТА И КООРДИНАЦИИ МЕРОПРИЯТИЙ

## 2.1 Общая архитектура системы

### 2.1.1 Архитектура системы

В качестве принятой архитектуры была выбрана клиент-серверная трёхуровневая архитектура с применением паттерна Controller-Service-Repository, опишем её назначение и преимущества.

Клиент-серверная архитектура – это модель взаимодействия в сети, где задачи разделены между поставщиками услуг (серверами) и запрашивающими услуги потребителями (клиентами). Клиент (браузер, приложение) отправляет запрос, а сервер обрабатывает его, обращается к базе данных и возвращает результат. Это обеспечивает централизованное управление данными, безопасность и масштабируемость [8].

Основные компоненты:

– Клиент: устройство или программа (веб-браузер, мобильное приложение), с которым взаимодействует пользователь. В разрабатываемой системе клиент реализован в виде SPA-приложения (Single Page Application) на основе библиотеки React и инструмента сборки Vite, обеспечивающих быструю и отзывчивую работу интерфейса.

– Сервер приложений: программное обеспечение, принимающее запросы, обрабатывающее бизнес-логику и хранящее данные. В разрабатываемой системе сервер реализован на платформе Node.js с использованием фреймворка NestJS, который обеспечивает строгую типизацию на основе TypeScript и модульную архитектуру.

– Сеть: среда передачи запросов и ответов по протоколу HTTP/HTTPS. Взаимодействие между клиентом и сервером осуществляется посредством REST API, документация которого генерируется автоматически с помощью Swagger.

Типы клиент-серверной архитектуры:

– Двухуровневая (2-tier): клиент напрямую взаимодействует с сервером.

– Трёхуровневая (3-tier): включает клиента, сервер приложений (бизнес-логика) и сервер баз данных.

– Многоуровневая (n-tier): сложная структура с дополнительными уровнями для масштабируемости.

В разрабатываемой системе применяется трёхуровневая (3-tier) клиент-серверная архитектура с паттерном Controller-Service-Repository, который обеспечивает чёткое разделение ответственности между уровнями приложения:

– Controller (Контроллер): принимает HTTP-запросы, проводит первичную валидацию входных данных и делегирует обработку сервисному слою;

– Service (Сервис): содержит бизнес-логику приложения, обеспечивает взаимодействие между контроллерами и слоем доступа к данным;

– Repository (Репозиторий): обеспечивает доступ к базе данных через ORM-инструмент Prisma, абстрагируя детали работы с СУБД.

Преимущества выбранной архитектуры:

– Централизация: удобное обновление данных и логики на сервере.

– Безопасность: данные защищены на сервере, клиент не имеет к ним прямого доступа. Аутентификация реализована на основе механизма JWT (JSON Web Token) с поддержкой access- и refresh-токенов.

– Масштабируемость: возможность наращивать мощности сервера без изменения клиентов. Контейнеризация посредством Docker и Docker Compose обеспечивает переносимость и воспроизводимость окружения.

– Типизация: применение языка TypeScript как на стороне клиента, так и на стороне сервера снижает количество ошибок времени выполнения и повышает качество кода.

### 2.1.2 СУБД системы

В качестве системы управления базами данных была выбрана PostgreSQL. PostgreSQL – это объектно-реляционная СУБД с открытым исходным кодом, которая на протяжении более чем тридцати лет активно развивается и заслуженно считается одной из наиболее мощных и надёжных в своём классе. Её выбор обусловлен рядом весомых технических и практических преимуществ.

Ключевые преимущества PostgreSQL.

– Полное соответствие стандарту SQL и поддержка ACID: PostgreSQL обеспечивает полную поддержку транзакций, соответствующих требованиям атомарности, согласованности, изоляции и долговечности (ACID). Это гарантирует целостность данных даже при сбоях системы, что критически важно для хранения информации о мероприятиях и регистрациях участников.

– Расширенные типы данных: в отличие от ряда других СУБД, PostgreSQL поддерживает тип данных UUID (используемый в схеме как первичный ключ), перечисления (ENUM), тип TEXT без ограничений длины, а также тип DECIMAL с точным хранением дробных чисел (применяется для координат геолокации).

– Высокая производительность при сложных запросах: PostgreSQL использует продвинутый планировщик запросов, поддерживает множество типов индексов (B-tree, Hash, GiST, GIN) и обеспечивает эффективное выполнение сложных JOIN-операций, необходимых при агрегировании данных об участниках и мероприятиях.

– Поддержка параллельных соединений: PostgreSQL использует архитектуру «процесс на соединение» и поддерживает множество одновременных подключений без деградации производительности, что соответствует нефункциональному требованию о поддержке 1000+ одновременных пользователей.

– Надёжность и безопасность: СУБД обеспечивает целостность данных через систему внешних ключей, каскадные операции (ON DELETE CASCADE, ON DELETE RESTRICT), триггеры и хранимые процедуры. Встроенные механизмы управления доступом позволяют разграничить права пользователей базы данных.

– Интеграция с ORM Prisma: выбранная СУБД обеспечивает первоклассную поддержку со стороны Prisma ORM – современного инструмента объектно-реляционного отображения для Node.js/TypeScript. Prisma предоставляет типобезопасный клиент, автоматическую генерацию миграций и декларативное описание схемы данных.

– Бесплатность и открытый исходный код: PostgreSQL распространяется под лицензией PostgreSQL License, совместимой с MIT, что позволяет свободно использовать СУБД как в учебных, так и в коммерческих проектах без каких-либо ограничений.

– Кроссплатформенность: СУБД функционирует на всех основных операционных системах (Linux, Windows, macOS) и в среде контейнеризации Docker, что соответствует выбранной инфраструктурной стратегии.

Для полноты картины приведём ограничения PostgreSQL:

– Повышенное потребление ресурсов памяти по сравнению с облегчёнными СУБД (SQLite, MySQL) при небольшом числе соединений;

– Более сложная начальная настройка по сравнению с MySQL, требующая дополнительных знаний администрирования.

Вместе с тем, для задач разрабатываемой системы, предполагающей работу со структурированными реляционными данными, необходимость строгой целостности ссылок и поддержку сложных аналитических запросов, PostgreSQL является оптимальным выбором.

В системе используется PostgreSQL версии 15, разворачиваемый в Docker-контейнере на основе официального образа `postgres:15-alpine`.

## 2.2 Проектирование модели данных

### 2.2.1 Сбор и анализ требований

Цель системы – координация студенческой активности, поэтому необходимо хранить данные в базе данных, в которой преобладают операции чтения и записи. Данные могут быть разного рода: текстовые, числовые, а также данные перечислимых типов (статусы, роли).

Определим ключевые сущности:

– Пользователи – это могут быть пользователи различных ролей: незарегистрированные (гости) и зарегистрированные. К зарегистрированным пользователям относятся: студенты, организаторы и администраторы. В отличие от классических подходов с раздельными таблицами для каждого типа пользователей, в данной системе применяется единая сущность «Пользователь» с полем роли (Role), что упрощает управление аутентификацией и авторизацией. Дополнительные атрибуты, специфичные для роли, выносятся в связанные профильные сущности. Таким образом, система включает следующие пользовательские сущности: «Пользователь» (User), «Профиль студента» (StudentProfile) и «Профиль организатора» (OrganizerProfile).

– Мероприятия – различные события, которые создаются организаторами для участников. Студенты регистрируются на мероприятия, если они им подходят. Сущность «Мероприятие» (Event) содержит основные данные: наименование, описание, тип, дату начала и окончания, адрес проведения, координаты, лимит участников, статус модерации, а также контактную информацию организатора.

– Регистрации – факты записи пользователей на мероприятия. Сущность «Регистрация» (Registration) фиксирует связь между студентом и мероприятием, хранит статус участия и данные о чек-ине (сканирование QR-кода).

– Изображения мероприятий – медиаматериалы, прикреплённые к мероприятию. Сущность «Изображение мероприятия» (EventImage) хранит ссылки на файлы изображений.

– Push-подписки – данные для отправки браузерных push-уведомлений (PWA-функциональность). Сущность «Push-подписка» (PushSubscription) хранит технические данные, необходимые для отправки уведомлений.

– Справочник институтов – нормализованный справочник учебных подразделений. Сущность «Справочник институтов» (InstituteDict) используется при заполнении профиля студента.

## 2.3 Проектирование бизнес-логики системы

### 2.3.1 Контекстная диаграмма

Контекстная диаграмма относится к категории диаграмм, описывающих систему на уровне «чёрного ящика» – а именно, только внешние свойства (в данном случае – потоки данных), но не содержание системы.

На рисунке 8 представлена контекстная диаграмма, которая показывает взаимоотношение программной системы с внешними сущностями.

Система координации студенческих мероприятий взаимодействует со следующими внешними сущностями:

– Неавторизованный пользователь: получает список опубликованных мероприятий и может пройти регистрацию или авторизацию в системе;

– Студент: записывается на мероприятия, получает личный кабинет с историей участия, управляет своим профилем, получает push-уведомления;

– Организатор: создаёт и редактирует мероприятия, просматривает списки участников, управляет чек-ином через QR-коды;

– Администратор: осуществляет модерацию мероприятий, управляет пользователями, получает сводную аналитику.

### 2.3.2 Диаграмма компонентов

Диаграммы компонентов используются для визуализации организации компонентов системы и зависимостей между ними. Они позволяют получить высокоуровневое представление об архитектуре системы [9].

Диаграмма компонентов представлена на рисунке 9.

Разрабатываемая система реализует архитектуру, состоящую из следующих ключевых компонентов:

**Клиентская часть (Frontend)** – SPA-приложение на основе React 18 и Vite, написанное на TypeScript. Состоит из следующих программных компонентов:

– Pages (Страницы): компоненты верхнего уровня, соответствующие маршрутам приложения (каталог мероприятий, карточка мероприятия, личный кабинет, регистрация, авторизация);

– UI-компоненты: библиотека Material UI (MUI) обеспечивает единообразный внешний вид интерфейса в соответствии с принципами Material Design;

– State Management: хранилище состояния реализовано на основе Zustand, кэширование серверных данных – с помощью TanStack Query (React Query);

– API Client: модуль взаимодействия с сервером на основе Axios, реализующий отправку HTTP-запросов к REST API и автоматическое обновление JWT-токенов.

**Серверная часть (Backend)** – приложение на основе фреймворка NestJS, написанное на TypeScript. Реализует паттерн Controller-Service-Repository и состоит из следующих модулей:

– AuthModule: обработка операций аутентификации и авторизации. Реализует регистрацию, вход, выход, обновление JWT-токенов. Применяет стратегии Passport.js (JWT-стратегия);

– UsersModule: управление пользователями, профилями студентов и организаторов;

– EventsModule: бизнес-логика работы с мероприятиями: создание, редактирование, фильтрация, публикация;

– RegistrationModule: обработка записи и отмены участия в мероприятиях;

– AttendanceModule: генерация QR-кодов и регистрация чек-инов участников;

– AdminModule: панель модерации, управление пользователями, аналитика;

– ReferencesModule: управление справочными данными (институты, типы мероприятий);

– PrismaService: сервис доступа к базе данных через Prisma ORM.

**База данных PostgreSQL** – реляционная СУБД для хранения всех структурированных данных системы.

**Кэш Redis** – хранилище типа «ключ-значение», используемое для управления сессиями, хранения refresh-токенов и очередей фоновых задач (BullMQ).

**Компонент «Инфраструктура» (Docker Compose)** – оркестратор контейнеров, обеспечивающий совместный запуск всех компонентов системы в изолированном окружении.

### 2.3.3 Диаграммы последовательностей

Приведём диаграммы последовательностей для основных операций в системе.

**Регистрация пользователя**

Рисунок 10 – Диаграмма последовательности регистрации пользователя

Опишем по пунктам всю последовательность операций.

1. Пользователь заполняет форму регистрации (логин, email, пароль, ФИО, роль и профильные данные) и отправляет данные на сервер.

2. Сервер проверяет корректность входных данных посредством декораторов class-validator, а также проверяет отсутствие пользователя с совпадающим логином или email.

3. Если проверка прошла успешно, сервер хэширует пароль с помощью алгоритма bcrypt и сохраняет в базу данных запись нового пользователя вместе с соответствующим профилем.

4. После успешного сохранения пользователю отправляется ответ об успешной регистрации.

**Авторизация пользователя**

Рисунок 11 – Диаграмма последовательности авторизации пользователя

Опишем по пунктам всю последовательность операций.

1. Пользователь отправляет на сервер логин и пароль.

2. Сервер выполняет запрос к базе данных на получение записи пользователя по указанному логину.

3. База данных возвращает запись пользователя либо сообщает об её отсутствии.

4. Сервер сравнивает предоставленный пароль с сохранённым хэшем посредством bcrypt. При совпадении генерируется пара токенов: краткосрочный access-токен (JWT, срок действия 15 минут) и долгосрочный refresh-токен (срок действия 7 суток).

5. Сервер отправляет пользователю пару токенов и данные профиля.

**Создание мероприятия**

Рисунок 12 – Диаграмма последовательности создания мероприятия

Опишем по пунктам всю последовательность операций.

1. Организатор, авторизованный в системе, заполняет форму создания мероприятия и отправляет данные на сервер.

2. Сервер проверяет JWT-токен и убеждается, что пользователь обладает ролью ORGANIZER.

3. Сервер проверяет данные на корректность (наличие обязательных полей, соответствие форматов дат).

4. Сервер делает запрос к базе данных на сохранение данных о мероприятии. Мероприятию присваивается статус MODERATION.

5. База данных возвращает ответ об успешном сохранении.

6. Сервер формирует ответ с данными созданного мероприятия и возвращает его организатору.

**Запись студента на мероприятие**

Рисунок 13 – Диаграмма последовательности записи на мероприятие

Опишем по пунктам всю последовательность операций.

1. Студент делает запрос на получение списка опубликованных мероприятий.

2. Сервер делает запрос к базе данных на получение списка мероприятий со статусом PUBLISHED.

3. База данных возвращает список мероприятий.

4. Сервер передаёт список мероприятий студенту.

5. Студент выбирает подходящее мероприятие.

6. После выбора мероприятия студент делает запрос серверу на запись.

7. Сервер проверяет наличие свободных мест (поле capacity) и отсутствие повторной регистрации того же пользователя на то же мероприятие.

8. Сервер отправляет запрос в базу данных на сохранение записи о регистрации.

9. База данных возвращает ответ об успешном сохранении.

10. Сервер возвращает студенту подтверждение регистрации с актуальными данными мероприятия.

## 2.4 Проектирование пользовательского интерфейса

### 2.4.1 Требования

Проектирование пользовательского интерфейса (UI-дизайн) – это не просто создание «красивых картинок», а процесс построения эффективного, удобного и эстетичного способа взаимодействия пользователя с продуктом (сайтом, приложением, программой).

Приведём требования к пользовательскому интерфейсу программного продукта.

– Функциональность: каждый элемент интерфейса должен решать конкретную задачу. Если кнопка не нужна – её удаляют.

– Интуитивность: интерфейс понятен с первого взгляда, использует привычные паттерны (иконки действий, навигационные меню, формы ввода).

– Отзывчивость: система мгновенно реагирует на действия (нажатие, наведение, скролл) визуальной обратной связью. Состояние загрузки отображается индикаторами прогресса.

– Простота: минимализм в деталях, но не в ущерб смыслу. Лучшее решение – то, которого пользователь не замечает.

– Типографика и типовые компоненты: для построения интерфейса применяется библиотека Material UI (MUI), реализующая принципы Material Design. Это обеспечивает единообразие визуального стиля, доступность (accessibility) и адаптивность под различные размеры экрана.

– Адаптивность: интерфейс должен корректно отображаться на экранах мобильных устройств, планшетов и настольных компьютеров. Поскольку система разрабатывается как PWA (Progressive Web App), она должна поддерживать установку на домашний экран мобильного устройства.

– Основные страницы должны содержать верхнюю навигационную панель с меню и кнопками аутентификации, основной контент и, при необходимости, нижний информационный блок.

## 2.5 Выбор среды разработки

Проведём обзор наиболее популярных сред программирования и выберем наилучшую для реализации проекта.

### 2.5.1 Microsoft Visual Studio

Visual Studio – это интегрированная среда разработки (IDE), разработанная компанией Microsoft, которая позволяет создавать приложения для различных платформ (включая Windows, Android, iOS и Linux). Предоставляет инструменты отладки, интеграцию с системами контроля версий, автоматическое тестирование и средства анализа кода.

Основным языком разработки является C#, предназначенный для платформы .NET. Visual Studio обладает широким набором функций для разработки корпоративных приложений, однако ориентирован преимущественно на экосистему Microsoft и имеет ограниченную поддержку JavaScript/TypeScript-разработки по сравнению со специализированными редакторами [10].

Интерфейс IDE Visual Studio представлен на рисунке 21.

### 2.5.2 IntelliJ IDEA

IntelliJ IDEA – ведущая интегрированная среда разработки компании JetBrains, которая делает разработку на Java и Kotlin более продуктивной. Выпускается в двух редакциях: Ultimate (коммерческая, полнофункциональная) и Community Edition (бесплатная, с открытым исходным кодом).

IntelliJ IDEA обладает продвинутыми функциями навигации по коду, рефакторинга, встроенным отладчиком и хорошей поддержкой веб-технологий в редакции Ultimate. Для разработки TypeScript/Node.js-приложений IntelliJ IDEA Ultimate является полноценным инструментом, однако требует платной лицензии [11].

Интерфейс IDE IntelliJ IDEA представлен на рисунке 22.

### 2.5.3 WebStorm

WebStorm – специализированная IDE компании JetBrains, предназначенная исключительно для JavaScript и TypeScript-разработки. Обеспечивает глубокую интеграцию с экосистемой Node.js, поддержку фреймворков React и NestJS, встроенный отладчик, линтинг кода и автодополнение на основе TypeScript. Является коммерческим продуктом с платной лицензией.

### 2.5.4 Visual Studio Code

Visual Studio Code (VS Code) – бесплатный редактор исходного кода с открытым исходным кодом, разработанный компанией Microsoft. Несмотря на позиционирование в качестве редактора, по функциональности VS Code приближается к полноценным IDE благодаря богатой экосистеме расширений.

VS Code обладает следующими ключевыми характеристиками:

– Первоклассная поддержка TypeScript: редактор разработан на TypeScript и для TypeScript, что обеспечивает наиболее точное автодополнение, навигацию по типам и встроенную диагностику ошибок;

– Широкая экосистема расширений: маркетплейс VS Code содержит более 50 тысяч расширений, в том числе официальные для ESLint, Prettier, Prisma, NestJS, Docker, PostgreSQL и Tailwind CSS;

– Встроенная интеграция с Git: визуализация изменений, управление ветками, работа с конфликтами непосредственно в интерфейсе редактора;

– Интегрированный терминал: поддержка нескольких терминальных сессий с возможностью запуска npm-скриптов, команд Docker и Prisma CLI;

– Отладка Node.js-приложений: встроенный отладчик с поддержкой точек останова, просмотра переменных и пошагового выполнения для приложений NestJS;

– Кроссплатформенность: доступен для Windows, macOS и Linux;

– Бесплатность: распространяется по лицензии MIT, что исключает затраты на лицензирование.

Интерфейс VS Code представлен на рисунке 23.

### 2.5.5 Обоснование выбора средств реализации

В качестве среды разработки выбран Visual Studio Code, в качестве платформы серверной части – Node.js с фреймворком NestJS, в качестве платформы клиентской части – React/Vite на языке TypeScript. Данный выбор обоснован следующими причинами.

– VS Code является бесплатным и свободным программным обеспечением, что исключает дополнительные затраты на лицензирование;

– TypeScript обеспечивает строгую статическую типизацию как на клиентской, так и на серверной стороне, что снижает количество ошибок и упрощает сопровождение кода;

– NestJS предоставляет зрелую модульную архитектуру, декораторы для описания маршрутов и валидации, встроенную поддержку Swagger, что ускоряет разработку и упрощает документирование REST API;

– React является наиболее популярной библиотекой для построения пользовательских интерфейсов, обладает обширной экосистемой и активным сообществом;

– Единый язык TypeScript на обеих сторонах позволяет повторно использовать типы и интерфейсы, что сокращает объём кода и исключает несоответствия между клиентскими и серверными структурами данных;

– Экосистема npm предоставляет все необходимые пакеты: Prisma ORM, class-validator, Passport.js, BullMQ, что ускоряет реализацию требуемой функциональности.

Среда разработки Microsoft Visual Studio не была выбрана, поскольку ориентирована преимущественно на разработку в экосистеме .NET и не обеспечивает оптимального опыта работы с Node.js/TypeScript-проектами.

Среда разработки IntelliJ IDEA не была выбрана, поскольку имеет платную лицензию в редакции Ultimate, необходимой для полноценной поддержки TypeScript, а бесплатная Community Edition обладает ограниченным функционалом для веб-разработки.

Среда разработки WebStorm не была выбрана по причине необходимости оплаты коммерческой лицензии при наличии функционально эквивалентной бесплатной альтернативы в лице VS Code с соответствующими расширениями.
